# Data loading

The app uses the in-memory client cache in `src/lib/client-cache.ts`; it does not need a second query library. The cache is shared across mounted screens, deduplicates simultaneous GETs, and is scoped to the authenticated user and clinic. It is never persisted to browser storage. `HarmonizeApp` waits for `/api/auth/me` before mounting private sections and clears the cache on logout or 401. A cross-tab session-change signal makes other tabs reload.

## Reading data

Use `getCachedJson<T>(key)` for ordinary authenticated GETs. `key` is the full resource URL, including patient ID, tab, journey ID, and filters. When rendering a revisited screen, `readClientCache<T>(key)` can populate state immediately; call `getCachedJson` in the effect to refresh stale entries. Keep an effect cleanup guard so a completed request cannot update a component after switching patient or tab. Do not use this cache for `/api/auth/*` or live appointment alerts.

Freshness/retention (milliseconds) is defined centrally by `policyFor`: agenda 20s/90s, dashboard 45s/180s, patient history 30s/120s, photo detail 60s/120s, catalogs/settings 5m/15m, other GETs 60s/5m. Retained stale data may be displayed while a new request runs. The cache has an 80-entry limit, including at most six photo-heavy entries.

## Changing data

After the server confirms a POST, PATCH, or DELETE, call `invalidateClientCache` with the exact keys or list prefixes affected. Invalidating `/api/patients` refreshes the patient list but does not remove every patient's history; invalidate `/api/patients/{id}/history` separately when the history changed. Failed mutations must leave cached data intact. The invalidation event can refresh mounted views that need immediate synchronization.

## API and database

List endpoints should return summaries with Prisma `select`, not entire relations or base64 image fields. Keep full photos and history behind patient-specific detail endpoints. Use clinic-scoped `where` clauses on every private query. Prefer a bounded, purpose-built endpoint for frequent polling (`/api/agenda/alerts`) over fetching a full bootstrap payload. Before adding pagination, account for client-side search/filter behavior so existing results remain complete.

## Paginated lists and on-demand loading

- **Clients.** `GET /api/patients?page&pageSize&q&status&sort` pages on the server: defaults page 1, `pageSize` 20 (max 100), `sort=name` (name, then id) or `recent`. Invalid or extreme values are clamped to safe values (never 400); a page past the end returns an empty list with the correct `pagination.total`. `q` searches name, phone and status ignoring case and accents. The response is `{ patients, pagination: { page, pageSize, total, pageCount }, summary: { total, byStatus } }`; `summary` always counts the whole clinic. Control characters (null byte) are stripped from `q` and `status`; ids that do not look like ids get 404. The accent-insensitive match runs `normalize(text, NFC)` in Postgres before `translate`, so names typed with decomposed accents are found too; this needs Postgres 13+ (local Docker is 16; Supabase hosts 15+). A search made only of digits and punctuation (3+ digits) also matches the digits of the phone in the list and of the CPF in the pickers, with or without mask. `GET /api/agenda` rejects dates outside 1970-2100 with 400. Build keys with `patientListKey` (`src/lib/patient-list-rules.ts`) so equal queries share one stable key. The screen debounces typing (300 ms) and keeps the previous page visible while the next one loads.
- **Patient pickers** (new appointment, quote, payment) never download every patient: they call `GET /api/patients/lookup?q&limit` (name or CPF, accent-insensitive, default 8 results, max 20, `q` shorter than 2 characters returns nothing; the pickers show "Digite pelo menos 2 letras") through `usePatientLookup` (300 ms debounce). `GET /api/patients/{id}` opens one profile that is not on the loaded page.
- **Agenda.** `GET /api/agenda/bootstrap` now has only static data (procedures, team, clinic hours). Appointments come from `GET /api/agenda?from=YYYY-MM-DD&to=YYYY-MM-DD` (inclusive, max 93 days, clinic scoped) for the visible day, week (Monday to Sunday) or month; `src/lib/agenda-period-rules.ts` computes the ranges and the neighbour periods that are prefetched. The automatic "Em atendimento" to "Atendido" step only sees the loaded period. The automatic "Faltou" step also uses `GET /api/agenda/overdue` (clinic scoped, read only): "Agendado" appointments whose end (date + time + real duration, clinic time zone) already passed, oldest first, max 200, never "Em atendimento" or "Atendido". The Agenda reads it once on mount (uncached, it drives a decision) and again after status changes, and feeds the same timer and PATCH.
- **Invalidation.** `invalidateClientCache("/api/patients")` drops every list page/search, the picker searches and the exact records `/api/patients/{id}`, but not sub-resources `/api/patients/{id}/...`; add `/api/patients/{id}` when a profile changed. For one appointment use `agendaDayInvalidationKey(day)` (`/api/agenda?day=YYYY-MM-DD`): only cached periods containing that day are dropped. Use `/api/agenda` when the day is unknown (all periods, bootstrap kept) and `/api/agenda/bootstrap` only when procedures, team or hours change.

## Verification

Run `node --test tests/client-cache.test.mjs`, `npx tsc --noEmit`, targeted lint, and a build after shared cache or API changes. For request-volume comparisons, record a fixed navigation flow with browser Network logs before/after; do not infer real byte savings or latency from static code alone. Authenticated browser measurements require a reachable database and test account.
